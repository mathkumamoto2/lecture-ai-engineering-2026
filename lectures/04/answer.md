これにより、用語集に記載されていない情報を補足する場合の判定基準を明確化した。

### 5. 気づき・疑問

今回の演習で、LLMによる自動採点では、採点基準を文章として定義するだけでなく、どのような境界事例をpass、fail、unsureとするかまで明確にする必要があると感じた。

特に、同じ回答でも評価する観点によって判定が変わる点が興味深かった。例えば、指示を無視して用語集を出力した回答について、範囲の基準ではfailとなる一方、出力された用語の正確性は別に評価する必要がある。

また、回の表示を文字列だけで判定する場合、存在しない第14回でもpassとなる問題がある。単純な文字列判定と、実際に講座の内容と整合しているかを確認する処理は分けて設計するべきだと考えた。

## 宿題

- 取り組んだレベル：Advanced（発展）

### 1. 調査対象

今回調査したベンチマークは **SWE-bench Verified** である。

公式URL：
https://www.swebench.com/verified.html

Hugging Face Dataset Viewer：
https://huggingface.co/datasets/SWE-bench/SWE-bench_Verified

SWE-bench Verifiedは、AIエージェントやLLMが実際のソフトウェア開発上の問題を解決できるかを評価するベンチマークである。

GitHub上の実際のIssueとソースコードを与え、問題を解決するコード変更（Patch）を生成させる。生成された変更を実際のテストで検証することで、ソフトウェア開発能力を評価する。

元のSWE-benchには、問題文の説明不足やテストの不備によって、正しい修正を行っても不合格になる問題があった。これらを改善するため、人間による検証を経て作成されたものがSWE-bench Verifiedである。

### 2. 実際の評価問題の確認

Hugging FaceのDataset Viewerで、実際の評価問題を5件確認した。以下はAstropyリポジトリに含まれる問題である。

| ID | 評価問題の概要 | データセット上の難易度 |
|---|---|---|
| astropy-12907 | ネストされたCompoundModelsに対して、separability_matrixが正しく計算されない問題 | 15分〜1時間 |
| astropy-13033 | TimeSeriesの必須カラム検証で、適切でない例外メッセージが発生する問題 | 15分〜1時間 |
| astropy-13398 | ITRS座標系内での座標変換処理を改善する問題 | 1〜4時間 |
| astropy-13453 | ASCIIテーブルのHTML出力で、指定したフォーマットが反映されない問題 | 15分〜1時間 |
| astropy-14182 | reStructuredText形式の出力でヘッダー行をサポートする問題 | 15分〜1時間 |

難易度はデータセットに登録されている値であり、コードベースに数時間慣れた経験豊富な開発者が修正する場合の所要時間の推定である。

これらを確認したところ、単純にエラーを修正するだけではなく、既存のライブラリの設計や内部処理を理解する必要がある問題が多いと感じた。

例えば、astropy-12907では複数のモデルを組み合わせた際の依存関係を理解する必要があり、astropy-13398では座標変換の仕組みそのものを理解する必要がある。

一方、astropy-13453やastropy-14182は、出力形式に関する問題であり、関連する実装とテストを確認すれば比較的取り組みやすいと考えた。

ただし、いずれも問題文だけで修正を完了できるわけではない。実際のリポジトリを調査し、既存の処理への影響を確認しながら実装する必要がある。

なお、今回確認した5件はViewer上で確認したAstropyの問題であり、全12リポジトリの問題を代表するランダムサンプルではない。

### 3. データセットの作成方法と検証

SWE-benchの元となる問題は、GitHub上の12のオープンソースPythonリポジトリから収集された、実際に解決済みのIssueとPull Requestで構成されている。

元のSWE-bench論文の著者は7名である。

SWE-bench Verifiedの作成では、OpenAIが元のSWE-benchの開発者と協力し、Pythonの経験を持つ93名のソフトウェア開発者による人手での品質検証を実施している。

具体的な作成・検証手順は以下のとおりである。

1. 元のSWE-benchから1,699件の問題をランダムに抽出する。
2. 問題文が十分に具体的であるか、テストが正しい解決方法を不当に排除していないかを確認する。
3. 1件につき異なる3名のアノテーターが独立して評価する。
4. 問題文の不明確さやテストの不備について、重大度を0〜3の4段階で評価する。
5. 3名の評価のうち最も重大度の高いものを採用し、重大な問題があるサンプルを除外する。
6. 残った問題から難易度の分布も考慮し、最終的に500件を選定する。

また、アノテーションを開始する前に、OpenAIのエンジニアが50件のサンプルを手作業で評価し、アノテーターの訓練用データとして使用している。

この検証では、問題文の不明確さや、正しい解答をテストが不当に不合格にする可能性などを確認している。

結果として、元の1,699件のうち68.3%が問題ありとして除外された。

このことから、評価データセットは問題を大量に集めるだけではなく、問題そのものと採点方法の妥当性を検証することが重要だと分かった。

### 4. 評価方法

SWE-bench Verifiedでは、LLMが生成したコード変更を実際のコードベースに適用し、ユニットテストを実行して評価する。

主に以下の2種類のテストが使われる。

- FAIL_TO_PASS：修正前には失敗し、正しい修正後には成功するテスト
- PASS_TO_PASS：修正前後の両方で成功し、既存機能が壊れていないことを確認するテスト

これらのテストがすべて成功した場合に、その問題を解決できたと判定する。

重要なのは、AIエージェントには評価用テストが事前に公開されず、Issueの説明と修正前のコードベースをもとに修正を行わせる点である。

これにより、単に正解を出力するだけではなく、既存のソフトウェアに対して実際に動作する修正を実装できるかを評価できる。

### 5. 今回の講座の評価セットとの比較

| 比較項目 | 今回の講座 | SWE-bench Verified |
|---|---|---|
| 評価対象 | 学習支援エージェントの回答 | ソフトウェア開発エージェント |
| 評価データ数 | 10件 | 500件 |
| 問題の作成 | 講師が事前に作成 | 実際のGitHub Issueから収集 |
| 人間による検証 | 学生がラベル付け | 93名の開発者が品質検証 |
| 1件あたりの検証者 | 演習では学生が判定 | 3名が独立して評価 |
| 評価方法 | 人間とLLMの判定を比較し、一部をコードで判定 | コード変更後のユニットテスト |
| 主な評価対象 | 根拠、範囲、ヒント、分かりやすさ | 実際のIssueを解決できたか |

両者の大きな違いは、評価対象と正解の判定方法にある。

今回の講座では、回答の正確性や適切さなど、文章としての品質を評価している。そのため、分かりやすさなど、人間によって判定が分かれる可能性のある基準も含まれている。

一方、SWE-bench Verifiedでは、コードを実行してテストが成功したかどうかを確認するため、比較的客観的な判定が可能である。

また、今回の講座の評価セットは10件であり、1名の講師が作成した回答を学生とLLMが評価する構成である。それに対してSWE-bench Verifiedでは、93名の開発者による検証と、1件につき3名の独立した評価を取り入れている。

この違いから、評価データの規模だけでなく、正解ラベルの信頼性を確保するための検証体制も重要であると考えた。

### 6. 調査を通じて気づいたこと・疑問

今回の調査で特に興味深かったのは、評価対象となるAIの性能だけでなく、評価データセットそのものの品質を検証するために、多くの人間が関わっている点である。

特に、1件の問題を3名が独立して評価し、重大な問題があれば除外するという仕組みは、評価結果の信頼性を高めるために重要だと感じた。

一方で、検証済みのデータセットであっても、必ずしも完全ではない。

2026年2月には、OpenAIがSWE-bench Verifiedの138件を追加調査し、そのうち59.4%でテスト設計や問題文に重大な問題が見つかったと報告している。また、公開リポジトリ由来の問題や解答がモデルの学習データに含まれる可能性も指摘されている。そのため、OpenAIはフロンティアモデルの性能評価にSWE-bench Verifiedを使用することを終了し、SWE-bench Proを推奨している。

この点から、評価データセットは一度作成して終わりではなく、モデルの進歩や利用状況に合わせて継続的に検証・更新する必要があると考えた。

今回の講座で実施した人間とLLMの判定の比較も、評価者であるLLM自体の信頼性を確認する取り組みとして重要である。

今後、自分でAIエージェントを開発する際にも、モデルの回答精度だけを見るのではなく、実際に達成すべき目的に応じた評価基準を設計し、人間による検証と自動評価を組み合わせることが必要だと感じた。
